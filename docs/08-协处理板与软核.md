# 08 协处理板、FPGA/软核与 dzframe/1

> 标注约定：**【已实测】** = 本仓库在 PC 上用测试/编译实际跑过（2026-10-28，Asia/Shanghai）；**【未验证】** = 设计意图或推断，尚未在真实硬件上做实验。实验是检验真理的唯一标准——【未验证】的内容上板前不要当结论。

协处理板（`kind: coprocessor`）不运行本框架 C 代码，只在 board.yaml 里描述与主控之间的**通道**：
- `class: linux_vision`：NVIDIA Jetson Nano、树莓派、地瓜派 RDK、MaixCAM2 等，Python 用 `host/python/dzlink` 收发。
- `class: fpga_logic`：FPGA 纯逻辑实现 dzframe 收发（预留）。
- **软核**（FPGA 内 RISC-V/MicroBlaze 等跑 C）：视为一块普通 MCU 板，新建移植层 + board.yaml，与主控同样用 dzframe/1 通信（预留）。

`tools/gen_coproc.py` 由通道定义生成主控侧 `cp_<角色>.{h,c}`（解包到结构体、新鲜度 age_ms）。

## dzframe/1 帧格式
```
A5 5A | VER(1) | KIND(1) | ID(1) | SEQ(1) | LEN(1) | PAYLOAD(0..64) | CRC16(2, LE)
```
- CRC-16/CCITT-FALSE（poly 0x1021，init 0xFFFF），覆盖 VER..PAYLOAD，check 值 0x29B1。
- 多字节字段显式小端；SEQ 用于丢帧统计；出错后从下一个 0xA5 重新同步。
- KIND：DATA / PARAM_SET / PARAM_ACK 等（见 dzframe.h）。

## Jetson Nano 侧（示意）
```python
from dzlink.protocol import encode, pack_fields, DATA
frame = encode(DATA, 1, seq, pack_fields(fields, {"x_px": x, "y_px": y, "found": 1}))
serial.write(frame)
```
发送端用 `dzlink.Sender`（docs/22）。部署/看日志（ssh、journalctl）还没做；原先的空壳 `workbench.py` 在 v0.7.0 审计时删掉了（全是 NotImplementedError、没人调用），真要做时再按实际设备写。

## 设计取舍（借鉴）
- 帧头 + 长度 + 序号 + ID + CRC：借鉴 MAVLink v1（https://mavlink.io/en/guide/serialization.html）。没选 MAVLink 本身，因为它的消息需 XML 生成器，对电赛小数据量偏重。
- 未采用 COBS（https://github.com/cmcqueen/cobs-c）：COBS 的定界更稳，但人眼看十六进制调试不直观；后续可作为 dzframe/2 候选。
- RoboMaster 裁判系统串口协议（SOF 0xA5 + 长度 + CRC8 头校验 + CRC16 整帧）同样是“定长头+CRC”的成熟做法，见 RoboMaster 官方《裁判系统串口协议附录》（https://www.robomaster.com/zh-CN/products/components/referee）。
- CRC 参数：Greg Cook CRC 目录（https://reveng.sourceforge.io/crc-catalogue/16.htm）。

## MaixCAM2 钢珠帧（2026H_ball 默认视觉协议）
- 描述：`boards/maixcam2-vision/board.yaml` 的 `ball` 通道，payload 7 字节：`flags u8 | x_px i16 | cam_ms u32`（小端），外层 dzframe/1（A5 5A 头、CRC16-CCITT-FALSE）。
- flags 沿用 P1 私有帧语义：bit0 有效、bit1 预测值、bit2 标定过期、bit3 识别到球；x_px 相对画面中心（解决了 P2 注释里“绝对/相对”自相矛盾的问题）。
- 相机端：`host/maixcam/ball_sender.py`（`find_ball()` 是占位，换成你的识别算法）；主控端：自动生成的 `cp_vision_cpu_ball_decode()`。
- 【已实测】PC 上 Python 编码 → C 解码互通（examples/2026H_ball/tests），帧前垃圾/CRC 错能重同步。【未验证】MaixCAM2 实机运行（MaixPy 接口未实测）。

## K230 视觉脚本库（直接复用参考仓库代码）
- 板描述：`boards/k230-vision/board.yaml`（class other，UART dzframe/1 115200）。通道 1 `target`（flags u8, x_px i16, y_px i16）、2 `ball`（flags u8 bit0 有效 bit1 预测, x_px, y_px i16, r_px u16）、3 `gimbal`（cmd u8, pan_x10 i16, tilt_x10 i16）。主控端解码：`python3 tools/gen_coproc.py boards/k230-vision/board.yaml -o <dir> --prefix k230`。
- 脚本：`third_party/vendored/k230_mspm0g_contest/`（矩形追踪→云台、矩形/形状/三角形检测、传感器诊断）。上游代码原样，只在发送函数开头加 `DZ_FRAME` 分支，经 `host/k230/dzsend.py` 发 dzframe；`DZ_FRAME = False` 回到上游原协议。来源与改动见各目录 SOURCE.md。
- 上板：把脚本和 `host/k230/dzsend.py` 一起拷到 K230 的 /sdcard（CanMV IDE），钢球脚本还要上游的 kmodel（不在本仓库）。
- 【已测-编译】`tools/test_k230_vision.py`（make check）：脚本里每个 `_dz.send` 的通道号和字段类型顺序与 board.yaml 一致；dzsend 编出的帧与 dzlink 参考实现逐字节相同。
- 【未验证】没有在 K230 上跑过任何一个脚本；EDC-Skill 上游未声明许可证，公开仓库前要先取得作者许可。

## 视觉链路：状态、延迟、跟踪、标定（2026-10）
| 环节 | 位置 | 做什么 |
|---|---|---|
| 相机端识别 | `host/maixcam/ball_tracker.py` | 自写跟踪器：只在预测位置附近的 ROI 里用颜色阈值找候选；用距离、面积突变、长宽比筛掉反光和线缆；α-β 平滑；漏检时最多外推 4 帧并置 predicted；连续丢 6 帧后回到全画面搜索 |
| 链路状态 | `firmware/algo/vision`（`vis_link`） | VALID / HELD / LOST 三态、age_ms、按 seq 计丢帧、相对延迟抖动。2026H 遥测里有 vis_state/vis_age_ms/vis_drops/vis_lat_ms |
| 标定 | `vis_calib` | 2..9 点分段线性，**中心两侧各 2 点以上（≥4 点）**时左右斜率独立。2026H 把原始像素映射成“线性化像素”（参数 cal_n、cal_px*、cal_v*），钢珠环增益不用改 |
| 延迟测量 | `python -m dzlink.latency stats/flash` | stats 看帧率、间隔 p95、丢帧、抖动；flash 用屏幕闪点法测绝对延迟，中位数可以作为 bb_lead_s 的起点 |

现场步骤：
1. 先跑 `latency stats`，确认帧率稳定、不丢帧。
2. 再跑 `latency flash` 拿到延迟。
3. 在摆杆上放钢珠，记录 5 个已知位置的像素，填 cal_* 参数。
4. 观察 vis_state：频繁 HELD 说明阈值或光照有问题。

【未验证】以上都没在实机上跑过；MaixPy 的 find_blobs 参数名按文档编写。
