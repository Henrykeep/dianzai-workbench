# 31 读题拆解与方案选型（10 步流程的第 1、2 步）

拿到题后的头几个小时决定后面三天：漏看一条规则、把耦合项当成两道题分开做，后面调得再好也拿不到分（2026H 复盘：漏看“循迹只能红外”“内壁不得增摩擦”“显示屏 ≤2 英寸”“图传要封存”，第 4–6 项共 60 分要求车和摆杆同时达标）。
这两步只做一件事：**把题目变成一份结构化文件，后面每一步都读它**，而不是每个人脑子里各记一份。

```
题目 PDF ──req.py init──▶ requirements.yaml（人工核对、三人签字）──req.py checklist──▶ 测试清单 md/csv（贴墙、逐项打勾）
                                   │
                                   └──scheme.py──▶ 方案对比（候选/替代/禁用原因）──▶ scheme.yaml（选定 + 理由 + 备选）
```

## 第 1 步 读题拆解：`tools/req.py`

| 命令 | 作用 |
|---|---|
| `python3 tools/req.py init 题目.pdf --code 2027X -o requirements.yaml` | 起稿：按“二、要求 1. 2.…（N 分）”或“基本要求/发挥部分（1）（2）”切出评分项，抓分值和原文里每个“数值+单位”（范围 a~b、±公差、≤/≥/不低于…比较、== 设定值/工作条件，名字从前文猜），按通用关键词表 `tools/catalog/needs_keywords.yaml`（可改）起草 needs，把“不得/只能/必须/封存/不予测试…”的句子列为候选规则约束。已存在不覆盖 |
| `python3 tools/req.py check requirements.yaml [--strict]` | 结构校验（schema/requirements.schema.json）；对照 project.yaml 核对子系统、`link.accept`、`tests` 编号；提醒：没指标（不可验收）、没分值、没映射子系统、规则未确认、整份未签字。`--strict` 让提醒也算失败（赛前用） |
| `python3 tools/req.py checklist requirements.yaml -o out/` | 生成测试清单：规则约束表（带确认框）、评分项 → 指标/测法/次数/子系统/工作台验收、子系统 × 评分项矩阵（标耦合）、各子系统牵涉分值、量级估算 |

模板：`docs/templates/requirements.yaml`。实例：`examples/2026H_ball/requirements.yaml`（`make check` 会对所有 `examples/*/requirements.yaml` 跑 check）。

设计取舍：
- **不让工具/AI 定稿**。init 只做文字切分和数字抓取，结果全部标“待填”；分值以外的含义（指标名、方向、子系统）必须人对照原文填。`problem.confirmed_by` 为空时 check 一直提醒。理由：设计文档第 1 步明确“人工逐条确认，避免 AI 误读题意”。
- **规则约束单列并带 `forbid/require` 标签**，第 2 步选型直接据此排除候选——“只能红外”不再靠人记。
- **子系统名必须是 project.yaml 里的**（ext: 前缀表示不在固件里：图传、机械、报告），这样测试清单和工程、工作台验收（docs/30）是同一套名字，不会两份各写各的。
- **指标必须是数**。“稳定”“尽快”这类写不成数的，check 报“不可验收”，逼着读题时把评委口径问清楚。

验证（[仿真]，即 PC 上跑）：2026 年 A–H 八道真题 PDF 全部能起稿；H 题起出 8 项、分值 6/16/13/20/20/20/5/20 与原文一致，复盘里漏看的 4 条规则全部进了候选约束（tools/test_req.py，原题 PDF 不进仓库，本机有才测）。局限：嵌套小问（如 G 题“（1）（2）”套在“1.”下）只切到小问，没有归属关系；评分表里的分值不读；表格/图片里的要求抓不到——起稿后必须人核对。

## 第 2 步 方案选型：`tools/scheme.py` + 器件库 `tools/catalog/parts.yaml`

| 命令 | 作用 |
|---|---|
| `python3 tools/scheme.py requirements.yaml -o out/` | `options.md`：第 1 步所有 `needs`（加上规则 `require`）按牵涉分值降序，每个能力列候选（仓库支持程度、优缺点、风险、替代件），被规则 `forbid` 排除的单列原因；最后是主控对比表 |
| `python3 tools/scheme.py requirements.yaml --init-scheme scheme.yaml` | 起稿 scheme.yaml（每项取排序第一名，全部“待定”），已存在不覆盖 |
| `python3 tools/scheme.py requirements.yaml --scheme scheme.yaml -o out/` | 核对选定方案并出 `scheme.md`（选定/理由/备选表 + mermaid 系统框图）。错误：件不在库、不提供该能力、被规则禁用、备选与选定是同一件、串口超限（选定件里 bus=uart 的个数 + 1 路调试链路 > 主控串口数）。提醒：有能力没选、选了没人需要的、≥20 分的能力没备选、用了仓库无驱动的件、串口刚好用满 |

器件库覆盖：主控 c8t6 / F407 VET6·VGT6 / MSPM0G3507；协处理器 Jetson Nano、MaixCAM(2)、K230、树莓派、RDK；传感器（红外灰度、编码器、MPU6050、BMI088、串口姿态模块、超声波）；执行器（直流 + H 桥、42 步进、QD4310、PWM 舵机）；按键、OLED/TFT、蓝牙串口。每个件都有 `repo:` 指向本仓库的驱动/板卡/发送库，`tools/test_scheme.py`（make check）检查这些路径存在——模块删了或改名，器件库会报错，不会悄悄过期。
加器件只改 parts.yaml（格式 schema/parts.schema.json）。

设计取舍：
- **排序只按“本仓库支持程度”**（上板 > 仿真 > 编译 > 无驱动）。性能好坏没有统一标尺，硬排会误导；写在 pros/cons 里给人权衡。目前全库没有一个“上板”——如实反映仓库现状（见 MORNING.md 硬件清单）。
- **规则约束自动生效**：第 1 步写了 `forbid: [sense.line_camera]`，摄像头循线就不会出现在候选里，选了也会报错。
- **scheme.yaml 是决策记录**：每项写理由和备选，是设计报告“方案论证”（2026H 3 分）的原料，也是赛中切换备选的依据。
- **串口核对是资源分配（第 3 步）的雏形**：只数串口，定时器/引脚冲突仍由 board.yaml + validate_board 负责，不在这里重复。
- 工具名不叫 select.py：放在 tools/ 下会遮住 Python 标准库 `select`（subprocess 依赖它）。

实例：`examples/2026H_ball/scheme.yaml`（用户比赛实际方案 + 复盘补写理由；图传 Jetson 标 `offboard`，不占主控串口）。make check 对所有带 scheme.yaml 的例题跑核对。
验证（[仿真]）：tools/test_scheme.py 5 项——2026H 规则 R4 排除摄像头循线、R5 排除 2.4 寸屏；把主控换成 c8t6 并改用串口 IMU 时报“串口不够”（4 > 3）。局限：价格、货源、重量、功耗没进库；不做多方案自动打分。

## 第 3 步 资源分配：`tools/alloc.py`

```bash
python3 tools/alloc.py examples/2026H_ball/scheme.yaml -o examples/2026H_ball/alloc --app examples/2026H_ball/app.yaml
# 已有板子/PCB（接线焊死了）：同名资源原样沿用，只分配剩下的
python3 tools/alloc.py examples/2026H_ball/scheme.yaml -o /tmp/alloc --fixed boards/stm32f407-bldc-freertos-cubemx/board.yaml
```

- **需求从哪来**：选定件在器件库里的 `res`（每件要占几路 GPIO/PWM/编码器/串口/I²C/SPI/ADC、逻辑名、频率、波特率、建议中断优先级），外加一路 `LINK` 调试串口；`offboard` 的能力不占主控资源。逻辑名冲突或要改名：scheme.yaml 里写 `names: {件id: {uart: [新名]}}`。
- **怎么分**：贪心，按稀缺程度先编码器（独占定时器，先用 TIM3/4/5/2，把 TIM1/8 留给 PWM）→ PWM（同一件的几路放同一定时器、同频）→ 串口 → SPI → I²C → ADC → GPIO（先用 PE/PD）。避开 `RESERVED_PINS`（SWD、晶振）和 `--fixed` 板上已占的脚。复用表就是 `tools/families/stm32f4.py`，与 `validate_board` 同一份。
- **怎么验**：草稿直接交给 `boardlib.check_board` + `check_requires`（和 `validate_board --app` 完全相同的检查），这里不另写规则；分不到的写 `TODO` 并在输出里列出来，不掩盖。
- **输出**：`board.yaml` 草稿、`cubemx.md`（逐项点 CubeMX：引脚与 User Label、定时器 PSC/ARR 按定时器所在总线时钟算好、编码器模式与滤波、串口 RX DMA 数据流（按表避开冲突）、NVIC 优先级表；用 FreeRTOS 时调 RTOS API 的中断整体 ≥5）、`alloc.md`（需求→结果→校验）。配完 CubeMX 后用 `tools/ioc_import.py` 导出的 board.yaml **覆盖**草稿——.ioc 才是唯一来源（docs/05）。
- **系列**：stm32f4（LQFP100，PA–PE）和 stm32f1（C8T6/CBT6 的 LQFP48，`tools/families/stm32f1.py`）自动分配。F1 没有逐脚 AF，是**整组重映射**（AFIO）：表里写成重映射组，分配器只在同一组里挑脚，boardlib 也按组检查（混用组 → `[重映射]` 错误）；PA15/PB3/PB4 上电是 JTAG、PC13 驱动弱，排在 GPIO 最后并给坑脚警告。mspm0 输出需求清单和全 TODO 草稿，引脚在 SysConfig 里人工定。
- **边界（如实）**：没算电流/走线，接线表的电流估算仍是缺口。2026H 例子的自动结果与真实的 bldc 板不同（例如自动把 PWM 放 TIM1、真实板用 TIM2），两者都过同一检查；有板子时用 `--fixed`。

## 证据与计分（req.py evidence）
评分项可写 `why`（为什么这样做能满足）、`forbidden_claims`（不能说的话）、`evidence`（指向 docs/verify 下的测试目录，层 unit/sim/bench/field）。
`python3 tools/req.py evidence requirements.yaml -o out/` 出五元组证据表；只有“现场通过”才能说已得分。目录规范与用法见 [docs/verify/README.md](verify/README.md)。
