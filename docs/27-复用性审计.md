## 0. 结论（先说结论）
- **骨架是对的，而且基本守住了"换板只改引脚"**：应用代码里不出现引脚号，资源靠逻辑名（`RES_*`），分层由 `check_deps.py` 强制，接口有版本锁。同一个应用换 F103/F407/MSPM0 编译都能过（下面 §1 实测）。
- **离"新人看 README 就能上手"还差一截**：卡点不在框架本身，而在上手路径——STM32 有两套移植层、两套板卡生成方式，Keil 流程从没在 µVision 里打开过，合成的 CubeMX 工程和 .ioc 可能不一致而且没人检查。
- **按做题流程逐步评级（§3，不给总百分比）**：通信/驱动/保护/调参工具现成，选板与控制环小改，建模/新传感器/场地联调/报告靠用户；**硬件 0 实测**，"90%"目前不能宣称。
- **最大的屎山风险点**是题目 io 胶水层（`examples/2026H_ball/io/io_main.c`，296 行、14 次修改、大量 `#if`）和 `Makefile`（327 行、47 次修改、三套芯片分支揉在一起）——这两处恰恰是新人和 AI 最常改的地方。

## 1. 模拟新人换板 / 换题
### 1.1 实测：只改一个引脚的新板【实测】
在仓库副本 `/tmp/porttrial` 里：复制 `boards/stm32f103c8t6-car-cubemx` → `boards/f103-trial`，把 .ioc 里 LED 从 PA8 改到 PC13，然后：
```
python3 tools/ioc_import.py boards/f103-trial/cubemx/f103car.ioc --base boards/stm32f103c8t6-car-cubemx/board.yaml -o boards/f103-trial/board.yaml
python3 tools/validate_board.py boards/f103-trial/board.yaml      # 错误 0 / 警告 1 / TODO 1
make BOARD=f103-trial APP=motor_speed_demo                          # 7.8 s 编过，Flash 32 KB
```
- 生成的 `board_gen.c` 里 LED 正确变成 `GPIOC, GPIO_PIN_13`。应用代码 0 改动。✔
- **问题 A（重要）**：`cubemx/Core/Src/main.c` 的 `MX_GPIO_Init` 仍然初始化 PA8——因为 Core 是"合成样例"，没有 CubeMX 重新生成。**构建没有任何检查发现 .ioc 与 Core 代码不一致**。真实用户会在 CubeMX 里 Generate，所以多半没事；但 AI 或新人只改 .ioc/yaml 时会编出"引脚表说 PC13、外设初始化在 PA8"的固件。
- **问题 B（重要）**：板卡写 `flash_kb: 64`，链接脚本 `STM32F103C8Tx_FLASH.ld` 写 `LENGTH = 128K`，size 报告按 128 KB 算百分比。C8T6 超过 64 KB 时不会报错。
- 问题 C（小）：stm32f1 没有复用/DMA 知识表，只做通用检查；`openocd_interface` 默认 TODO。

**结论（按步骤，不按行数）**：通信、驱动（已有器件）、保护机制、调参工具这些"每题都要写、容易写错"的部分是现成的；选板定引脚和控制环是小改；建模、新传感器、场地联调、报告仍是用户自己的。比赛里真正吃时间的是第 6、8 步（实物调参、场地联调），框架能缩短迭代但不能替代，而且**这些步骤都还没在真硬件上验证过**——所以"90% 以上"目前不能对外宣称。

### 4.2 逐仓库深读（问题 → 核心手法与出处 → 我们对比 → 采纳什么、落在哪）
> 路径相对 `/workspace/refs/`（box 上的克隆，见 refs/STUDY-INDEX.md）。行号为本次读到的版本。

**① PID_Helper + F1/H7/C3 例程（gitee qianmonai，GPL-3.0，只借思路）**
- 解决的问题：一套上位机（Electron）+ 同一协议在三颗芯片上的下位机，让学生不写串口代码就能调 FOC 速度/位置环。
- 核心手法：
  - 协议与硬件解耦靠**回调注入**：`qianmonai-pid_-helper_-stm32-h7_-example/User/pid_helper_protocol.h:65-83` 定义 `TxFn / OnPidFn / OnModeFn / OnOutputFn / OnSetpointFn`，协议层只解帧、调回调；但 `TxFn` 返回 `HAL_StatusTypeDef`（同文件 :65），协议头仍绑着 HAL——换到 ESP32 例程时只能整份重写一遍。
  - H7 发送用**固定深度的 DMA 发送队列**：`Core/Src/main.c:57-59,91,104`（`TX_QUEUE_SIZE 4`，每槽一帧，遥测不阻塞控制）。
  - 内外环共享内环：`User/foc_dev.c:142-156` 速度环与位置-速度双环共用 `speed_pid`，切模式时 `PID_Reset`。
  - 帧格式 `AA 55 cmd seq arg0 arg1 arg2 sum`（`PID_Helper/README.md:217`），只有 8 位累加和；`PID_Helper/openspec/changes/…/{proposal,design,tasks}.md` 用 OpenSpec 管理需求变更。
- 我们对比：我们的协议层 `firmware/proto/dzframe` 不依赖任何 HAL（check_deps 强制），换芯片不用重写，**这点比它好**；校验用 CRC 也更稳。我们缺的是"同一应用每颗芯片一份可直接打开的最小工程"，以及模式切换时显式复位内环的约定。
- 采纳：G5 每主力板 `examples/<板>-minimal`；在 `firmware/framework/subsys` 文档里写明"on_mode 必须复位所属 PID"（对照 foc_dev.c:153）；LINK 发送队列深度与"控制优先、遥测可丢"对照 H7 做法核查（G9 附带）；不采纳 8 位累加和、不采纳协议头绑 HAL。
