# 23 质量审计（v0.7.0，2026-10-29，Asia/Shanghai）

目标：客观找出“屎山”苗头，真问题小步重构，不为改而改。方法：按文件行数排查、vulture 找死代码、文档里的路径逐个核对是否存在、重复代码 grep、按用户实际流程（Keil 编译 → Agent 烧录 → 上车）走一遍调用链。每一步后 `make check / test / cross` 全绿。

## 结论（先说重点）
整体分层是健康的：`check_deps` 强制单向依赖、`iface_hash` 强制版本号，模块间没有发现越层 include；最大的手写文件 `pal_stm32f4.c`（868 行）是一个端口的全部外设，按外设分节，暂不拆。真正的问题不在“代码长”，而在**两处调用链断了、测试却是绿的**，这比风格问题危险得多：

| # | 问题 | 严重度 | 处理 |
|---|---|---|---|
| A1 | 编译结果从没交给烧录器：`Flasher.note_build` 只有测试调用，Agent 没有 `build` 工具。真用起来烧录前置条件 `build_ok` 永远不满足，烧录永远被拒 | 高（功能不可用，但方向是安全的） | 已修：新增 `build` 工具，`build_log` 也登记；日志与镜像时间差 >120 s 不登记。加测试 |
| A2 | host-sim 的 `pal_adc_info` 写死分压 1/1，board.yaml 的 `scale_num/den` 在仿真里不生效 → 电池 CRIT 急停在仿真里永远不会触发（v0.6.0 记为“只编译未跑通”的根因） | 高 | 已修：gen_board 生成 `g_host_adc_info[]`；test_car 加 CRIT 急停 + 锁存用例 |
| A3 | car_2wd 急停时控制中断直接 `continue`，不更新编码器 → 遥测里转速冻结在急停前的值，上位机看着像还在转 | 中（误导调试） | 已修：急停时照常更新编码器 |
| A4 | 天空星两块板 VBAT 的 `scale_num: 1`（等你填分压）→ 读数是真实电压的 1/11，“先见过 OK”永远不成立，**电池保护在真板上实际是关着的** | 中（安全功能静默失效） | 没擅自改：分压比要看你的板子。已写进 MORNING 和 QUESTIONS 45 |
| B1 | gen_board.py 四个端口生成器各写一遍 ADC 初值格式串 | 低 | 已抽成 `_adc_info()`，生成结果逐字节一致 |

| B3 | 文档路径漂移 3 处：`mechanical/.gitattributes`（实际在根目录）、`tools/shot.py`（实际 `app/tools/`）、`tests/test_batch3.py`（实际 `app/sidecar/tests/`） | 低 | 已改 |

## 看过但不改（理由）
- **`clampf` 在 4 个模块里各有一行**（ball_beam、servo、drive_plan、2026H ball）。模块设计成可以单独拷进 Keil 工程，为一行函数引入公共头会让每个模块多一个依赖、改动 common 层接口。一行的重复比多一层依赖便宜，保留。
- **K230 `dzsend.py` 与 `dzlink/protocol.py` 重复实现 CRC/编码**：K230 的 MicroPython 跑不了 dzlink（QUESTIONS 43），重复是有意的，`test_dzsend_k230` 逐字节对比两边，不会悄悄走样。
- **测试里两处 ADC 原始值换算小函数**（test_modlib、test_car）：测试代码，各自独立更好读。
- **vulture 报的 `MockProbe` / `MockBackend` / `require_swarm` 等**：测试替身和测试入口，不是死代码。
- **`pal_stm32f4.c` 868 行、`pal_mspm0.c` 620 行**：一个端口一个文件是 docs/02 的约定，便于整体替换；里面按外设分节、无重复逻辑。等再加 DMA 等大功能时按外设拆。
- **`session.py` 492 行、`agent/service.py` ~450 行**：职责单一（链路会话 / Agent 工具实现），暂不拆；service 再长下去时把“编译/烧录/变量”拆成 `agent/toolchain.py`。

## 命名与分层抽查
- 模块前缀一致（`xxx_init / xxx_update / xxx_selftest`、`XXX_VERSION`）；新加的 rtosmon 照此命名。
- FreeRTOS 相关只出现在 `ports/stm32-cubemx/dz_freertos.*`，应用只依赖纯逻辑的 `firmware/framework/rtosmon`，CubeMX 的 USER CODE 区没有加任何新行（check_deps C1 把关）。

## 以后每个版本都跑一遍的检查
1. `python3 -m vulture app/sidecar/dzbench tools host/python --min-confidence 60`，逐条判断。
2. 文档路径核对（本次用的脚本思路：抓 md 里 `tools/ ports/ app/ …` 开头的路径，`os.path.exists`）。
3. **按用户真实流程走一遍调用链**：这次最大的两个问题都是“单元测试绿、但生产代码里没人调用”，只有走流程才看得出来。

# v0.8.0 “真的接上了吗”（2026-10-29）

方法：每个用户能碰到的入口（界面按钮、Agent 工具、命令行工具、固件选项），按用户的操作顺序从入口打到仿真板再看回来的结果。`app/sidecar/tests/test_wiring.py` 还做静态对照：界面发的 op 侧车都认、侧车每个 op 都有界面入口或写明的脚本用途、Agent 每个工具都有实现和风险等级、human 级工具在确认卡上有中文名——以后加按钮忘了接线，测试会红。
