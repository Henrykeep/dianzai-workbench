# 13 版本管理、分支与提交约定

## 两层版本
1. **仓库版本**：git 附注标签 `vMAJOR.MINOR.PATCH`（`git tag -a v0.3.0 -m "..."`），与 CHANGELOG.md 的章节一一对应。0.x 阶段接口仍可能调整。
2. **模块版本**：每个模块目录的 `VERSION` + 头文件里的 `XXX_VERSION` 宏（check_deps V1 核对一致）。接口变化规则由 `tools/iface_hash.py` 强制（docs/03）：
   删除/修改公开声明 → 升 MAJOR；只新增 → 至少升 MINOR；只修实现 → PATCH。改完运行 `python3 tools/iface_hash.py --update`。

## CHANGELOG
- 每次合入在「未发布」下按 新增 / 变更 / 修复 / 移除 记一条，末尾必须标验证程度：**[上板] [仿真] [编译] [未测]**。
- 发布时把「未发布」改成 `## [x.y.z] - 日期`，打同名附注标签，推送：`git push origin main --follow-tags`。
- 上板实测后，在对应条目补 `[上板 日期 板卡]`，不要删除原标记以外的历史。

## 分支
- `main`：始终 `make check && make test` 通过、所有板卡可交叉编译。
- 功能分支 `feat/<主题>`、修复 `fix/<主题>`、比赛现场 `comp/<年份><题号>`（只收参数与题目代码，赛后挑选合回 main）。
- 发布只从 main 打标签。

## 提交信息
- 格式：`<范围>: <做了什么>`，范围用目录名（`pid`、`ports/stm32-cubemx`、`boards`、`docs`、`tools`…），一行说清，必要时空一行写原因。
- 一个提交只做一件事（逻辑提交）；生成文件（iface.lock.json、testdata 期望）与引起它变化的代码同一提交。
- 提交前：`make check && make test`；改了板卡或移植层再跑相应 `make BOARD=...`。
